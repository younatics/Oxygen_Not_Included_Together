# 판정 기준이 틀리면 초록은 아무 의미가 없다

이 세션에서 **다섯 번** 같은 종류의 실수를 했다. 매번 한두 라운드를 엉뚱한 곳에 썼고,
매번 코드가 아니라 **측정 방법**이 원인이었다. 순서대로 적는다.

| # | 무엇을 성공으로 봤나 | 실제 | 어떻게 드러났나 |
|---|---|---|---|
| 1 | 채굴 **지정**이 되면 성공 | 아무것도 안 팠다 | 사용자가 화면을 보고 지적 |
| 2 | 시나리오가 끝까지 돌면 성공 | **일시정지 상태**로 돌았다 | `paused=True` 를 뒤늦게 확인 |
| 3 | `WorldDamageSpawnResource` 가 host 로그에 없으면 미발생 | 클라만 로그를 남긴다 | 26개를 캔 실행을 "채굴 없음" 으로 판정 |
| 4 | 완료 패킷이 로그에 1줄이면 전송 안 됨 | 그 패킷들은 **로그를 안 남긴다** | `PacketTracker` 계측: 27 송신 / 27 수신 |
| 5 | `(종류, 프리팹, 셀)` 로 객체를 짝지음 | **이동한 객체가 둘로 세어진다** | id 로 키를 바꾸니 불일치 2 → 0 |

## 규칙

**1. 로그 부재는 사건 부재가 아니다.**
로그를 안 남기는 코드가 대부분이다. 흐름을 알고 싶으면 **카운터를 노출**해서 재라
(`PacketTracker.DumpCounts`, `previewsCreated/Adopted`, `LookupFailCount`, `CollisionCount`).

**2. 양쪽 로그를 항상 짝지어 본다.**
한쪽만 보면 비대칭이 안 보인다. `analyze-session.ps1` 의 패리티 표가 이 규칙의 구현이다.
`host 1 / client 27` 같은 행이 곧 발견이다.

**3. 지시가 아니라 결과를 판정한다.**
"지정했다"·"명령을 보냈다"·"패킷을 만들었다" 는 성공이 아니다.
광석이 스폰됐는지, 셀이 비었는지, 객체가 양쪽에 있는지를 본다.

**4. 불변식을 적용할 대상을 먼저 확인한다.**
두 번 실패했다 — 연속 id 휴리스틱은 셀을 정상적으로 XOR 하는 building 경로를 버그로 읽었고,
"한 칸에 id 하나" 는 한 칸에 겹쳐 선 복제인간 셋을 버그로 읽었다.
**정상 구현과 버그를 구분하지 못하는 테스트는 없느니만 못하다.**

**5. 정체성은 id 로 짝짓는다. 위치는 상태지 정체성이 아니다.**
움직이는 것(운반 중인 광석, 크리터, 복제인간)은 셀이 갈린다. 그걸 불일치로 세면
멀쩡한 시스템이 고장나 보이고, 실제로 두 라운드를 그렇게 날렸다.

**6. 되돌림도 결과다.**
이 세션에서 5건을 되돌렸다(스윕 배칭, 스윕 입양, 클라 생성 차단, 주기 단축 ×2).
전부 **숫자가 나빠져서** 되돌렸고, 되돌린 이유를 커밋 메시지에 남겼다.
그 기록이 다음 시도의 출발점이 된다 — 특히 "차단은 통지가 즉시일 때만 성립한다" 는
두 번의 실패에서만 나올 수 있는 결론이었다.

**7. 회귀를 먼저 의심한다.**
"전엔 됐는데 지금 안 된다" 는 신고가 두 번 다 맞았다.
breakoff 제거로 피어 내부 id 충돌을 만들었고, 스윕 배칭으로 클라 상태를 지웠다.
새 코드가 아니라 **내가 바꾼 것**부터 본다.

## 검증 순서 (이 순서로 하지 않으면 위 실수가 반복된다)

1. **빌드** — 컴파일은 최소 조건이지 검증이 아니다
2. **양쪽 배포 + sha256 대조** — 다른 바이너리로 잰 수치는 해석 불가
3. **실제 세션** — `run-scenario.ps1`, 일시정지 해제 확인, 양방향 지시
4. **계측 읽기** — `packets` 덤프, 패리티 표, `netid_compare`, `diff_logs`
5. **수정 전후 숫자 비교** — 개선 없으면 되돌린다

## 아직 신뢰하면 안 되는 것

- `run-scenario.ps1` 의 "no mining observed" 경고 — 호스트 로그를 보는데
  그 패킷은 클라에만 남는다. **고치기 전까지 무시한다** (실수 #3 이 그대로 남아 있음)
- `selfcheck_log.py` 의 섹션 B — building 경로에는 적용되지 않는다(로그를 안 남기므로
  현재는 무해하지만, workable 로깅이 바뀌면 실수 #4 가 재발한다)
