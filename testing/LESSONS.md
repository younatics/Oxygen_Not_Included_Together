# 판정 기준이 틀리면 초록은 아무 의미가 없다

이 세션에서 **다섯 번** 같은 종류의 실수를 했다. 매번 한두 라운드를 엉뚱한 곳에 썼고,
매번 코드가 아니라 **측정 방법**이 원인이었다. 순서대로 적는다.

| # | 무엇을 성공으로 봤나 | 실제 | 어떻게 드러났나 |
|---|---|---|---|
| 1 | 채굴 **지정**이 되면 성공 | 아무것도 안 팠다 | 사용자가 화면을 보고 지적 |
| 2 | 시나리오가 끝까지 돌면 성공 | **일시정지 상태**로 돌았다 | `paused=True` 를 뒤늦게 확인 |
| 3 | `WorldDamageSpawnResource` 가 host 로그에 없으면 미발생 | 클라만 로그를 남긴다 | 26개를 캔 실행을 "채굴 없음" 으로 판정 |
| 4 | 완료 패킷이 로그에 1줄이면 전송 안 됨 | 그 패킷들은 **로그를 안 남긴다** | `PacketTracker` 계측: 27 송신 / 27 수신 |
| 5 | `(종류, 프리팹, 셀)` 로 객체를 짝지음 | **이동한 객체가 둘로 세어진다** | id 로 키를 바꾸니 불일치 2 → 0 |

## 규칙

**1. 로그 부재는 사건 부재가 아니다.**
로그를 안 남기는 코드가 대부분이다. 흐름을 알고 싶으면 **카운터를 노출**해서 재라
(`PacketTracker.DumpCounts`, `previewsCreated/Adopted`, `LookupFailCount`, `CollisionCount`).

**2. 양쪽 로그를 항상 짝지어 본다.**
한쪽만 보면 비대칭이 안 보인다. `analyze-session.ps1` 의 패리티 표가 이 규칙의 구현이다.
`host 1 / client 27` 같은 행이 곧 발견이다.

**3. 지시가 아니라 결과를 판정한다.**
"지정했다"·"명령을 보냈다"·"패킷을 만들었다" 는 성공이 아니다.
광석이 스폰됐는지, 셀이 비었는지, 객체가 양쪽에 있는지를 본다.

**4. 불변식을 적용할 대상을 먼저 확인한다.**
두 번 실패했다 — 연속 id 휴리스틱은 셀을 정상적으로 XOR 하는 building 경로를 버그로 읽었고,
"한 칸에 id 하나" 는 한 칸에 겹쳐 선 복제인간 셋을 버그로 읽었다.
**정상 구현과 버그를 구분하지 못하는 테스트는 없느니만 못하다.**

**5. 정체성은 id 로 짝짓는다. 위치는 상태지 정체성이 아니다.**
움직이는 것(운반 중인 광석, 크리터, 복제인간)은 셀이 갈린다. 그걸 불일치로 세면
멀쩡한 시스템이 고장나 보이고, 실제로 두 라운드를 그렇게 날렸다.

**6. 되돌림도 결과다.**
이 세션에서 5건을 되돌렸다(스윕 배칭, 스윕 입양, 클라 생성 차단, 주기 단축 ×2).
전부 **숫자가 나빠져서** 되돌렸고, 되돌린 이유를 커밋 메시지에 남겼다.
그 기록이 다음 시도의 출발점이 된다 — 특히 "차단은 통지가 즉시일 때만 성립한다" 는
두 번의 실패에서만 나올 수 있는 결론이었다.

**7. 회귀를 먼저 의심한다.**
"전엔 됐는데 지금 안 된다" 는 신고가 두 번 다 맞았다.
breakoff 제거로 피어 내부 id 충돌을 만들었고, 스윕 배칭으로 클라 상태를 지웠다.
새 코드가 아니라 **내가 바꾼 것**부터 본다.

## 검증 순서 (이 순서로 하지 않으면 위 실수가 반복된다)

1. **빌드** — 컴파일은 최소 조건이지 검증이 아니다
2. **양쪽 배포 + sha256 대조** — 다른 바이너리로 잰 수치는 해석 불가
3. **실제 세션** — `run-scenario.ps1`, 일시정지 해제 확인, 양방향 지시
4. **계측 읽기** — `packets` 덤프, 패리티 표, `netid_compare`, `diff_logs`
5. **수정 전후 숫자 비교** — 개선 없으면 되돌린다

## 아직 신뢰하면 안 되는 것

- `run-scenario.ps1` 의 "no mining observed" 경고 — 호스트 로그를 보는데
  그 패킷은 클라에만 남는다. **고치기 전까지 무시한다** (실수 #3 이 그대로 남아 있음)
- `selfcheck_log.py` 의 섹션 B — building 경로에는 적용되지 않는다(로그를 안 남기므로
  현재는 무해하지만, workable 로깅이 바뀌면 실수 #4 가 재발한다)

## 8. 경고 문구가 호출자를 안 밝히면, 그 경로는 안 보이는 것과 같다

라이브 세션 호스트 로그에 `[PacketSender] No connection found for SteamID 0` 이 **26분간 5436줄**
있었다. 초당 3.5건, 줄지 않고 일정. 그런데 이 문구에는 **패킷 이름이 없어서** 어느 요청-응답
경로가 깨졌는지 알 수 없었고, 그래서 여러 세션을 그냥 지나쳤다.

원인은 `NetworkConfig.GetLocalID()` 가 `MultiplayerSession.IsClient` 로 분기한 것이었다.
`IsClient` 는 `InSession` 을 요구하는데, Riptide 클라는 **접속 직후 id 가 이미 유효**하고
`InSession` 은 더 뒤에 켜진다. 그 창에서 클라는 *서버* id — 호스팅 안 하는 PC 에선 0 — 를 반환했다.

**짧은 창이 영구 증상을 만든다.** syncer 는 스폰하자마자 호스트에 상태를 요청하고 그 id 를 찍는다.
0번 플레이어의 요청은 접수는 되고 **응답만** 실패한다. 응답을 못 받은 syncer 는 쿨다운마다 다시 묻는다.
초기화 순서 문제 하나가 세션 내내 침묵으로 남는 구조다. 화면에 보인 건 "클라에서만 고장난 화장실"
하나뿐이었다.

규칙:
- **실패 로그는 무엇이 실패했는지 말해야 한다.** 수신자 id 만으로는 부족하다. 이름과 횟수를 같이.
- **같은 경고가 초당 여러 번이면 그건 재시도 루프다.** 한 줄씩 찍지 말고 묶어서 세라 —
  5436줄은 진단을 가리는 동시에 DEBUG 빌드에서 그 자체로 비용이다.
- **정체성은 세션 플래그가 아니라 연결을 실제로 쥔 쪽에서 나와야 한다.**

# 2부 — 내가 만든 회귀에서 배운 것

1부는 **측정**이 틀린 이야기였다. 이 아래는 **수정**이 틀린 이야기다.
하루 동안 회귀를 여섯 번 만들었고, 여섯 번 다 컴파일을 통과했고, 여섯 번 다 라이브에서만 드러났다.

| # | 내가 한 것 | 실제로 벌어진 일 | 어떻게 드러났나 |
|---|---|---|---|
| 1 | `void` 메서드에서 `__result` 를 읽음 | Harmony 패치 실패 → **모드 전체 미로드** → 양쪽 게임이 안 켜짐 | 사용자가 "게임이 안 켜진다" |
| 2 | 셀에 객체가 생겼는지로 건설 판정 | 건설 주문이 그 프레임에 항상 나타나진 않음 → **오더 21개 중 3개 유실** | 사용자가 "설치 오더가 안 보인다" |
| 3 | 충돌 경고에서 `?.name` | 파괴된 Unity 객체는 `?.` 로 안 걸림 → **호스트 예외 261건** | 호스트가 죽음 |
| 4 | 건설 현장에 신원 부여 | 현장과 완공 건물이 같은 셀·프리팹·레이어 → **재배치 5,617건** | 로그 상위를 이것이 도배 |
| 5 | 체력을 `Int` 로 쓰고 `.Float` 로 읽음 | 항상 0으로 해석 → **클라가 자기 건물을 매번 전파괴** | 사용자가 "화장실이 클라만 고장" |
| 6 | 늦게 붙인 신원도 등록하게 함 | 정리 중인 객체에도 등록 시도 → NRE | 배포 직후 로그 |

## 규칙 (1부에 이어서)

**8. 컴파일은 게임 API 에 대해 아무것도 보장하지 않는다.**
Harmony 파라미터, Unity 의 가짜 null, 태그 유니온의 필드 선택 — 셋 다 컴파일 타임에 검증되지 않는다.
`dotnet build` 가 통과했다는 건 **문법이 맞다**는 뜻이지 동작한다는 뜻이 아니다.

**9. 실패의 폭발 반경을 먼저 줄인다.**
오늘 가장 값어치 있던 변경은 기능 수정이 아니라 **패치를 하나씩 적용하게 만든 것**이었다.
`Harmony.PatchAll` 은 첫 실패에서 전체를 중단한다 — 그래서 잘못된 패치 하나가 게임을 못 켜게 만들었다.
이제는 실패한 클래스 이름을 남기고 건너뛴다. 대가는 "기능 하나 빠짐"이지 "게임이 안 켜짐"이 아니다.

**10. 진단 코드가 사고를 낼 수 있다.**
`?.name` 한 줄이 호스트 로그에서 가장 많은 예외가 됐다.
**문제를 설명하는 게 유일한 목적인 코드는, 문제를 만들 수 없어야 한다.**

**11. 수정하면서 검증 수단을 지우지 마라.**
손상 불일치 경고를 없애고 수정을 넣었더니, **"손상이 안 일어난 세션"과 "고쳐진 세션"이 로그상 똑같아졌다.**
결과를 남기되 **값과 함께** 남긴다. `damage replicated` 는 참이면서 쓸모없었고,
`30 -> 0 of 30` 이었으면 한눈에 틀린 걸 알았다.

**12. 조용한 폐기는 미구현과 구분되지 않는다.**
`if (!_tracked.TryGetValue(...)) return;` 하나가 와이어 상태를 영구히 끊었는데,
**연결한 적 없는 와이어와 완전히 같은 모습**이었다. 버리려면 말하고 버린다.

**13. 로컬 키는 영구적이지 않다.**
등록 시점의 NetId 를 키로 잡으면, id 가 바뀌는 순간 그 항목은 **아무도 보내지 않을 주소**에 갇힌다.
레지스트리로 해석하는 경로는 이 문제가 없다 — 가능하면 그쪽을 쓴다.

**14. 세션 경계는 프로세스 경계가 아니다.**
플레이어는 재접속하고 호스트는 저녁에 하드싱크를 여러 번 한다.
살아남은 정적 상태는 **두세 번째 세션에서만** 터지고, 그때는 원인이 전혀 다른 곳처럼 보인다.
"이미 진행 중" 플래그 하나가 그 프로세스의 하드싱크를 영구히 막았다.

**15. 도구가 틀리면 결론도 틀린다.**
정규식 교대 순서 때문에 `.ByteArray` 가 `Byte` 로 잡혀 멀쩡한 코드를 불일치로 보고했다.
청크 폐기 2,144건은 **테스트가 일부러 만든 것**이었다. 분석 스크립트도 검증 대상이다.


**16. 세션 상태와 월드 상태는 다르다. 섞으면 데이터가 지워진다.**
세션 경계에서 정적 상태를 청소하다가 `PlantTracker.AllPlants` 까지 비웠다.
그런데 **호스팅 시작이 `MultiplayerSession.Clear()` 를 부른다** — 월드가 멀쩡히 로드된 채로.
식물은 `Growing.OnSpawn` 에서만 등록되므로 이미 서 있는 식물은 다시 채워지지 않는다.
결과: 호스트가 **헤더뿐인 빈 스윕 22개**를 보냈고, 부재로 조정하는 클라가 **자기 식물 294개를 지웠다.**

월드는 세션보다 오래 산다 — 호스팅을 켰다 껐다 해도 콜로니는 그대로다.
세션 것(구독, 전송 큐, 시퀀스, 진행 중 플래그)은 **비우고**,
월드 것(식물·걸레·소독 추적, 애니메이션 syncer)은 **죽은 항목만 솎아낸다.**

**17. 부재로 조정하는 수신자에게 빈 스냅샷은 폭탄이다.**
"전부 없음"과 "송신자가 자기 목록을 잃음"이 **같은 패킷으로 도착한다.**
콜로니가 진짜로 식물 0개가 될 수는 있으니 거부가 답은 아니지만,
**조용히 전멸시키는 것**은 답이 아니다. 지금은 보유분이 있는데 빈 스윕이 오면 거부하고 이유를 남긴다.
고칠 대상은 송신자인데, **피해가 안 보이면 고칠 수가 없다.**

## 수정을 배포하기 전 체크리스트

1. 이 패치가 건드리는 게임 API 가 **정말 그 시그니처인가** (`void` 인데 `__result` 를 읽지 않는가)
2. 이 코드가 **파괴된 객체**를 만날 수 있는가 (`?.` 는 Unity 에서 안전하지 않다)
3. 새로 만든 id/키가 **기존 것과 충돌**하지 않는가 (같은 셀·프리팹·레이어를 쓰는 다른 객체가 있는가)
4. 쓰는 타입과 읽는 필드가 **같은가** (태그 유니온은 변환하지 않는다)
5. 실패했을 때 **로그에 값이 남는가** (사실만 남기고 숫자를 빼지 않았는가)
6. 이 상태는 **세션이 끝날 때 정리되는가** — 그리고 그게 **세션 것이 맞는가**(월드 것을 지우고 있지 않은가)
7. 부재로 조정하는 수신자에게 **빈 스냅샷**을 보낼 수 있는 경로인가
