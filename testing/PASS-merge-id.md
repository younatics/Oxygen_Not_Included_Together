# 합격 조건 — 병합 시 id 승계 (잡동사니, 마지막 항목)

실행 **전에** 적는다. 이 항목은 한 번 시도해 되돌렸고(리졸버 요청 억제 → 클라가 객체 30여 개를
더 놓침), 화면에 안 보인다는 이유로 안 고치기로 했던 것이다. 이번엔 다른 지점을 친다.

## 근거 숫자 (직전 빌드에서 다시 잰 것)

```
gaveUpRetired  37, 37     클라가 받았다가 스스로 병합해 없앤 id
손 계산        30, 29     그중 호스트가 여전히 갖고 있는 것
정체           전부 Oxygen · DirtyWater · Water · Methane · CarbonDioxide · Hydrogen · Dirt
chore PEER-ONLY  39~60    prio PEER-ONLY 120
```

리졸버는 이걸 못 닫는다. 호스트가 답하고(원소 답변 207건/실행) 클라가 id 를 붙여도, 클라의
시뮬레이션이 그 더미를 **또** 합쳐서 id 가 다시 은퇴한다.

## 무엇을 바꿨나

`Pickupable.Absorb(pickupable)` 프리픽스. `this` 가 살아남고 인자는 다음 줄에서 삭제된다.
**먹힌 쪽에 번호가 있고 살아남은 쪽에 없을 때만** 번호를 옮긴다.

둘 다 번호를 가진 경우는 **일부러 건드리지 않는다.** 살아 있는 소유자를 밀어내는 override 가
`PlantGrowthSyncer.EnsureIdentity` 주석이 기록한 그 사고다 — 분당 4회에서 430~460회로 올라가
세션이 끝날 때까지 안 내려온 것. 그 경우는 `mergeBothNamed` 로 세기만 한다.

## 합격 조건

| # | 조건 | 뜻 |
|---|---|---|
| 1 | `mergeIdMoved > 0` | 변경이 발동했다. **0 이면 판정 불가**, 지표를 근거로 쓰지 않는다 |
| 2 | 클라 `gaveUpRetired` 가 37 → **20 이하** | 실제로 줄었다 |
| 3 | 클라 `errors = 0` | |
| 4 | `netid_compare exit 0` 유지 | **id 가 엉키지 않았다 — 이게 가장 중요한 안전 조건** |
| 5 | `idMoves` 가 폭주하지 않음 (직전 380~390 수준) | 교환 루프가 안 생겼다 |

**4번이 깨지면 즉시 되돌린다.** id 를 잘못 옮기면 호스트가 A 에 대해 보낸 패킷이 클라의 B 에
적용된다 — 이 저장소가 `NetId -1258014647` 사례로 이미 겪은 것이고, 화면에 안 보이는 병합보다
훨씬 나쁘다.

**1번 없이 2번만 맞으면 판정 불가로 적는다.** `gaveUpRetired` 는 실행마다 흔들리는 값이다.

## 이 변경이 답할 수 없는 것

- 양쪽 더미가 **둘 다 번호를 가진** 병합은 그대로 어긋난다. `mergeBothNamed` 가 그 크기다.
  이 실행의 목적 중 하나는 그 숫자를 처음 보는 것이다.
- `chore`/`prio` PEER-ONLY 가 크게 줄 것으로 기대하지 않는다. 그 행들은 클라가 일을 안 해서
  생기는 것도 섞여 있다. **줄지 않아도 회귀가 아니다.**
