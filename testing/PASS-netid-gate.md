# 합격 조건 — 포기한 NetId 를 분류해서 게이트가 무엇인지 말하게 하기

실행 **전에** 적는다.

## 왜 이 변경인가 — 측정된 것

`FAIL client NetId | No registry lookup failures` 는 매 실행 실패했고 STATUS 목록에도 없었다.
빌드 `10DC528F` 2회 실행의 두 peer id 덤프를 손으로 갈랐다:

```
        포기   지금 여기 있음   호스트가 갖고 있음   양쪽 다 없음
run 1    39          2                29                8
run 2    41          5                30                6
```

호스트가 갖고 있던 59개는 **전부** `Pickupable` 기체·액체·흙 더미였다
(Oxygen, DirtyWater, Water, Methane, CarbonDioxide, Hydrogen, Dirt, ContaminatedOxygen).
건물 0, 듀플 0, 플레이어가 가리킬 수 있는 아이템 0.

클라 자신의 인구조사가 같은 id 에 이미 정확한 이름을 붙이고 있었다:
`this peer had it and retired it`. 즉 **이건 새 결함이 아니라 STATUS 3번 잡동사니 병합**이고,
게이트가 그것을 다른 이름으로 부르며 매 실행 빨간불을 켜고 있었다.

패킷은 유실되지 않았다: 요청 341 보냄 / 340 도착, 답 348건(unknown 118 + prefab 23 + element 207).

## 이 변경이 하는 일

포기한 id 를 **읽는 시점에** 레지스트리에 물어 셋으로 가른다.

| 갈래 | 뜻 |
|---|---|
| `gaveUpPresent` | 늦게 도착했다. 보정 경로가 스폰 응답에는 없어서 영원히 실패로 남던 것 |
| `gaveUpRetired` | 받았다가 스스로 놓았다 — 병합. 결손이 아니다 |
| `gaveUpNever` | 한 번도 가진 적 없다 — **이것만 진짜 결손** |

게이트는 `gaveUpNever` 로만 실패한다. 나머지 둘은 실패 메시지와 통과 메시지 **양쪽에** 실린다.

## 합격 조건

| # | 조건 | 뜻 |
|---|---|---|
| 1 | `gaveUpRetired` 가 25~35 | 손으로 센 29·30 을 코드가 재현한다. **여기서 크게 벗어나면 분류가 틀린 것** |
| 2 | `gaveUpPresent` 가 2~6 | 손으로 센 2·5 |
| 3 | `gaveUpNever` 가 0~2 | 진짜 결손은 거의 없다 |
| 4 | 클라 `NetId` 검사 FAIL 소멸 | 1~3 이 맞을 때만 의미가 있다 |
| 5 | 클라 `errors=0` 유지 | |

**4번 하나만으로 판정하지 않는다.** 검사를 통과시키는 가장 쉬운 방법은 검사를 눈멀게 하는
것이고, 1~3 이 손으로 센 값을 재현하는지가 그것과 진짜 분류를 가른다.

`gaveUpNever` 가 3 이상이면 **분류가 맞더라도 진짜 결손이 남아 있다는 뜻**이므로, 그 id 들의
프리팹을 호스트 덤프에서 확인한다. 건물이나 듀플이 하나라도 있으면 그건 별개의 결함이다.

## 이 변경이 답할 수 없는 것

- 병합 자체는 **고치지 않는다.** 행 수는 그대로일 것이다. 이건 게이트가 무엇을 보고 있는지
  바로잡는 변경이지 desync 를 줄이는 변경이 아니다.
- `state_compare` 는 계속 exit 1 일 것이다. `chore`/`prio` PEER-ONLY 가 같은 원인이다.
